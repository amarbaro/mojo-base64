# mojo-base64 v0.1.1

**Released:** 2026-11-07 · **Commit:** `f2444a9` · **Previous:** [v0.1.0](v0.1.0.md)

## What it does

Base16, Base32, Base32hex and Base64 byte codecs for Mojo, matching CPython 3.14.8/3.14.9 `base64` bytes and full error messages. Pure Mojo, no Python at run time. Compile from a clone with `-I src`; see README and `docs/api.md`.

## Highlights

<!-- 1 to 5 bullets a user would notice. Lead with the benefit, not the implementation. -->
- Base64 and Base16 now run 1.8-5.4x faster than v0.1.0 and faster than CPython at 1 KiB and 64 MiB (b64encode 1.23 vs 0.77 GB/s, b64decode 1.28 vs 0.64, b16decode 1.30 vs 0.47).
- Codecs allocate only the result: exact capacity, no scratch, no per-call table build; decode errors leave the caller's `out` untouched.
- A decode bug with `altchars` is fixed (see Fixed).

## Changes

### Added
- 1500 seeded random differential rows (4042 goldens, was 2494) and `tools/gen_vectors.py SEED COUNT OUT` for scratch fuzz files.
- b16 rows in the benchmark and its CPython reference; 7 more mutants (22).
### Changed
- b64 and b16 kernels write through a pointer into reserved capacity; static 64 B/256 B alphabet and decode tables; urlsafe decode and encode use the fast path.
- `scripts/nightly.sh` requires `MOJO_NIGHTLY`; no machine path.
### Fixed
- `b64decode(..., altchars=...)`: altchars are validated and applied before the leading `=` check, as in CPython (`altchars=b'=_'` with `validate=True` and a leading `=`; bad altchars length with leading `=`).

## Known limits

<!-- Honest list: slow paths, unsupported cases, flaky upstreams, anything UNVERIFIED. -->
- Base32 is append-based and not benchmarked or tuned.
- Peak RSS of the b64 benchmark is 7.7% above CPython (270144 vs 250828 KB): allocator retention of freed large blocks; the result itself has capacity == length.
- Python exception types differ; String inputs, encode altchars, Base85 and wrapping are unsupported.
- Feeding a span of `out` to its own `_into` call is unsupported (the reserve may move it).
